# 🧭 Haylen Plugins — project guide

This repository holds the native plugins of [Haylen](https://github.com/haylen-org/haylen) apps, one folder each named after the id of the plugin: the plugins of the optional capabilities of the device and the system, built on the APIs of each platform alone, and the plugins of third-party SDKs. It also holds the lab apps `plugin-lab` and `pack-lab`, which check the plugins of SDKs and of store delivery on every platform.

This file is binding for every change. It describes the repository as it is and the rules every change follows. Each plugin has an `AGENTS.md` of its own with the rules and the checks of that plugin, which this file does not repeat. When a rule changes, update the file that holds it in the same change and describe the new state in the present tense.

## Core principles

- Every plugin follows the `AGENTS.md` of the Haylen repository and the plugin format of its `docs/platform/plugins.md`: naming, the writing, comment and clean-code standards and the requirements of each platform.
- No shortcuts, hacks, silent fallbacks, dead or obsolete code or compatibility paths. Fix root causes and remove what a change supersedes. Unknown input is an explicit error.
- A flaw of the engine is fixed in the engine, never worked around in a plugin. When a plugin needs something Haylen lacks, Haylen gains the capability first.
- A plugin never gets around a restriction, a permission or a policy of a platform. A limit is an explicit error, a documented requirement or a documented gap.
- Code, comments and documentation are written in English. Never mention other engines. A plugin names the SDK it wraps, its company and the platforms and stores it targets.
- The repository never records its own history. Code, comments and docs describe what exists now, and git holds the history.
- The plugins are free for personal and commercial work, forever, under the MIT License of `LICENSE`, and every contribution becomes part of them under the same license.

## Plugins

- A plugin is a folder with `plugin.json` of the plugin interface 1, with its `implementations`, `dependencies`, `permissions`, `parameters` and typed `contributions`, `README.md`, `AGENTS.md`, the Lua API in `source/` and a native part for each platform it serves: `apple/`, `android/`, `web/` and `native/`, whose desktop libraries are C++20 classes behind the C entry point of `HaylenNative.h` that read and write their JSON with nlohmann/json and build with `find_package(haylen CONFIG REQUIRED)` and the target `haylen::native` of the engine SDK. Each plugin keeps the `.gitignore`, `.editorconfig` and `.clang-format` of `templates/plugin` of Haylen, byte for byte, so a copy of the plugin in an app keeps them, and the `.gitignore` of the root also keeps out what builds write into the plugin folders.
- The Lua API of a plugin is the same on every platform. A platform that cannot serve a call fails it with a code and a sentence that says why, and a platform where the plugin has no native part is `lua` in its `implementations`, a gap that its README states with the reason. Every plugin lists every platform, so an app that uses it builds everywhere.
- A capability that a platform gates is a permission that the plugin declares in `permissions`, registers through the plugin [`permissions`](permissions) on each native part and asks for through it before each use, so the plugin lists `permissions` in its `dependencies`: `Permissions.register(_:on:)` and `Permissions.require(_:on:)` on Apple platforms, `Permissions.register` and `Permissions.require` of `com.haylen.plugins.permissions` on Android, and `registerPermission` and `requirePermission` of `haylen-plugin:permissions` on the web, while a desktop library answers `<id>.permission` and `<id>.requestPermission` itself. Its Lua module declares the permission with `permissions.declare`, and the app checks and asks for it with `<id>.permission()` and `<id>.requestPermission()` of the plugin, or with `permissions.state(name)` and `permissions.request(name)`. Two plugins never declare the same permission, so a plugin that builds on the permission of another one lists it in `dependencies` and the app asks through that plugin.
- On Apple platforms the plugin [`notifications`](notifications) owns the delegate of the notification center, which it sets as its plugin class loads, before launching ends. Every other plugin that posts or receives notifications lists `notifications` in its `dependencies`, adopts its Swift protocol `NotificationsDelegate` and registers with `Notifications.addDelegate(_:)` from the `load(with:)` of its plugin class, and never sets the delegate of the center itself.
- A third-party SDK stays at its latest release, pinned exactly: Swift packages with `exactVersion`, Gradle dependencies with a version, and web scripts at an address that names the version. A newer release is adopted as soon as it exists, with its current API everywhere.
- The README of a plugin documents its installation from this repository, its parameters, its setup on each platform, its complete Lua API with examples, its native API and what each platform answers. Every change updates it.
- The plugins of system capabilities each have a sample app in `sample/` that references the plugin with `"path": ".."`, and samples keep no platform projects, since every build generates the project of its target. The plugins of SDKs are checked in `plugin-lab` and `pack-lab`, which reference them with `"path": "../<id>"` and use placeholder keys and the test ids of each SDK alone.
- No key, keystore, real configuration file of a service or account value ever enters the repository. Placeholder configuration files name no real project.

## Verify

- Every plugin builds and runs on every platform it declares, in a test app that references it, and `haylen app build` verifies each target. On Apple platforms it also runs in a C++ app. The `AGENTS.md` of each plugin lists its own checks.
- Simulators, the Android emulator and the browser carry the checks, and a physical device runs only what they cannot show, such as the camera, the microphone, the sensors, Bluetooth, real purchases, ads with fill and push delivery.
- Every check is automatic. The sample of a plugin of a system capability keeps UI tests of every call of its plugin, in Swift in `sample/ui-tests/apple` and in Kotlin in `sample/ui-tests/android`, which `haylen test --ui sample` runs on the simulators and the emulator, on the devices of this machine with `--target ios`, `tvos` or `android` and `--device`, and on the phones of AWS Device Farm with `--device-farm`. They answer the prompts and the dialogs of the permissions, tap the notifications and press the buttons of the system, so no check asks a person to tap anything. A sample whose web part answers what the browser decides keeps a driver of the debugging protocol of Chrome in `sample/ui-tests/web`, which presses the buttons of the mirror of the UI that the page keeps for screen readers, reads the log there and sets the permissions of the site, as the README of `permissions` shows.

## Publishing

- The repository keeps exactly one commit on `main`, which every change amends and force-pushes, with no tag and no release. Apps that want to stay on one version name that commit in the `ref` of their entry.
- Before every commit, review what is staged and make sure nothing private or generated goes in: build outputs, caches of Gradle and Kotlin, keys and keystores, and files of Finder and the editors.
